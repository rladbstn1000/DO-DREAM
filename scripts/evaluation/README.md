# 5단계 고정 합성 평가

이 폴더는 네트워크를 사용하지 않는 자료 준비·관측 기록 집계 도구다. 실제 공급자 호출 승인이나 실행 기능은 없다. `plan.json`의 승인은 항상 false이고 키도 받지 않는다. 실제 실행은 별도의 승인·예산 guard와 기존 인증·발행·색인·채점 앱 경로를 거쳐야 한다.

직접 작성한 추가 자료 2개에는 각각 서로 다른 본문 8구간이 있다. 각 본문은 content-v1 청킹에서 정확히 한 청크이며, top3가 자료 전체를 가져오지 않는다. 기존 직접 작성 자료 2개의 **신규 복사본**은 스모크용으로만 사용한다. 실제 준비는 새 자료 ID를 발급받고 기존 자료를 수정하지 않는다.

- `corpus.json`: 학생에게 공개 가능한 평가 본문 16구간.
- `smoke_manifest.json`: 기존 `student-web-v1`의 물·분리배출 본문 복사본과 스모크 순서. 검색 지표에서 제외한다.
- `server_quizzes.json`: 서버 준비용 질문·정답 20개. 검색기·학생 본문·답변 입력에 전달하지 않는다.
- `rag_gold.json`: evaluator 전용 24문항. 직접 질문·고정 대화 의존·답 없음 각 8개, 개발/최종 각 12개. 각 분리는 서로 다른 개념으로 구성했다.
- `grading_gold.json`: evaluator 전용 16답안. 명확한 정답 4, 바꿔 쓴 정답 4, 부분 정답 3, 오답 3, 부정 표현 2. 개발/최종 각 8개이며 같은 질문의 표현만 바꿔 분리하지 않았다.
- `plan.json`: 고정 모델·청킹·top3·입출력 상한·A/B 유일 변경점·실행 순서·캐시·분모 정의.
- `freeze.json`: 실제 모델 출력을 보기 전에 고정한 파일 및 전체 자료 SHA-256. 입력이 달라지면 검증이 실패하며 기존 freeze를 덮어쓰지 않는다.

이것은 내부 합성 평가셋이다. 전문가 검증 데이터나 실제 학생 평가가 아니며, 개념 중복 검사는 사람이 작성한 `concept_id`와 동일 질문 탐지를 검사한다. 자동 검사가 두 문항의 의미적 독립성까지 증명하지는 않는다.

저장소 루트에서 실행한다.

```bash
python3 -m unittest discover -s scripts/evaluation/tests -v
python3 scripts/evaluation/phase5.py validate
python3 scripts/evaluation/phase5.py export
python3 scripts/evaluation/phase5.py review
```

`export`는 허용 필드로 새 객체를 만들어 공개 본문·질문·동일한 이전 대화만 내보낸다. 기대 내용·정답 근거 ID·rubric·판정은 제외한다. 서버 퀴즈는 별도 파일로 준비한다. 실제 채점 요청은 이 파일에서 임의로 구성하는 대신 서버의 3-A attempt snapshot을 읽어야 한다.

`review`는 `.local/phase5/evaluation/`에 날짜별 HTML과 집계 JSON을 새로 만든다. 외부 이미지·스크립트·글꼴이 없는 작은 로컬 검토표이며, 관측이 없으면 답변·실행·사람 검토는 `NOT_RUN`, 점수·비용은 null이다. 기존 출력 파일은 덮어쓰지 않는다. 실제 승인 실행 후 한 번의 관측 JSON 배열을 제공할 수 있다.

```bash
python3 scripts/evaluation/phase5.py review --records .local/phase5/evaluation/실행별-관측.json
```

관측 형식은 `phase5.py`의 `validate_record`로 검사한다. 자료 키·원본 버전·frozen hash, case ID, A/B, 실행 상태, 실제 답변·abstained, 검색/전달/인용 구간 ID, 단계별 시간, 실제 요청 수, usage, 계산 비용·예약 비용, cold/warm을 기록한다. 사용량을 모르면 null이며 timeout을 무료로 계산하지 않는다. `map_runtime_sources`는 실제 앱의 원본 hash·청크 위치·내용 hash와 실제 인용 ID를 안정적 구간 ID로 바꾼다. 정답 근거 목록을 검색 결과 대신 사용할 수 없다.

Hit@3의 분모는 실행한 근거 있는 문항이며 오류·timeout은 miss로 포함한다. 계획된 근거 문항은 비교군마다 16개다. 미실행은 관측 분모에서 제외하되 실행 수·계획 수를 함께 기록하고 불완전 결과는 `PARTIAL`로 남긴다. 답 없음 8개는 응답의 `abstained` 관측 비율과 의미 검토를 구분한다. 채점 일치는 실행한 16개 고정 기대 판정과 비교하며 실패를 오답 판정으로 바꾸지 않는다.

답변 의미와 근거 충실성은 검토표에서 따로 살핀다. 자동 source ID 검사나 고정 채점 기대값 비교가 사람 검토 PASS가 되지 않는다. 이 도구는 사람 검토를 자동으로 PASS로 바꾸는 기능이 없다. 개발 도구의 판단을 추가할 경우 별도 `자동 예비 검토`로 표시해야 한다. 유료 심판 모델은 사용하지 않는다.

A는 현재 질문, B는 대화가 있는 문항에서 검색 질문 재작성만 추가한다. 두 방식은 같은 자료·원본·모델·top3·답변 prompt·상한·고정 대화를 사용한다. 생성된 A 답변을 B의 이전 대화로 사용하지 않는다. 실행 순서는 개발/최종을 분리하며 같은 split에서 문항별 AB/BA를 번갈아 사용한다. 공급자 prompt cache는 통제할 수 없으므로 cached usage를 기록하고 애플리케이션 답변·질의 임베딩 cache는 사용하지 않는다. 첫 요청은 cold, 이후 warm으로 표시하고 유료 warmup은 하지 않는다.

실행 프로세스가 처음 요청했는지 확인할 수 없는 관측은 `cold:null`로 기록하고 cold/warm과 분리해 집계한다. 특히 채점 서버에 브라우저 요청이 섞일 수 있어 최초 요청을 관측하지 않았다면 warm으로 추정하지 않는다. RAG 평가 CLI는 문항마다 새 프로세스이므로 각 문항은 process-cold다. 이는 Chroma 저장소 cache나 공급자 cache까지 비어 있음을 뜻하지 않는다. 고정 계획의 cold/warm 분류를 관측하지 못한 범위는 한계로 남기며, null을 warm 표본으로 합산하지 않는다.

집계 비용은 해당 관측들의 범위다. 스모크·UI·실패·재시도를 포함한 작업 전체 비용은 공통 영속 guard 원장에서 가져온다. 원장과 겹치는 관측 비용을 두 번 더하지 않는다. 예약액, 관측 usage로 계산한 비용, 실제 청구 확인은 다르다. 소수 표본 지연을 운영 SLA로 제시하지 않는다. 최종 결과를 본 뒤 prompt를 바꾸면 탐색 결과로 보존하고 독립 검증이라고 부르지 않는다. B 채택은 실제 쌍별 결과와 별도 의미 검토 전까지 보류한다.
